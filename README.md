# EnhancedNativePlayer

A tvOS video engine that plays any remote MKV / MP4 through `AVPlayer` by losslessly remuxing it into HLS (fMP4) on the fly, served from a small HTTP/1.1 server of its own on Network.framework, bound to loopback. Video `AVPlayer` can't decode (AV1, VC-1, MPEG-4 Part 2, …) is decoded by the engine and drawn under the same system controls. FFmpeg 9.0 is built by `scripts/build-ffmpeg.sh` with only what the engine uses, plus the small fixes in `scripts/patches/ffmpeg`, into dynamic frameworks under `Frameworks/` (dav1d inside libavcodec for AV1), and libass by `scripts/build-libass.sh`. The package uses those when they are there, and otherwise downloads the ones `scripts/release.sh` attached to the package's GitHub release.

```swift
import EnhancedNativePlayer
import SwiftUI

struct MovieView: View {
    @State private var player = EnhancedPlayer()

    let media = EnhancedMedia(
        url: URL(string: "https://server/movie.mkv")!,
        headers: ["Authorization": "Bearer \(token)"],
        title: "Dune",
        description: "…",
        artwork: .url(posterURL),
        subtitles: [ExternalSubtitle(url: URL(string: "https://server/movie.en.srt")!, language: "en")]
    )

    var body: some View {
        EnhancedPlayerView(player)
            .ignoresSafeArea()
            .task(id: media) {
                try? await player.load(media, startTime: .seconds(120))
                player.selectedSubtitleTrack = player.subtitleTracks.first { $0.language == "en" }
                player.play()
            }
    }
}
```

The API has three parts, like `AVPlayer`, its media and `VideoPlayer`:

- **`EnhancedMedia`** is what to play: the URL and its headers, what the info panel and Now Playing show (`title`, `subtitle`, `description`, `artwork`, `genre`, `contentRating`, `releaseDate`), `chapters` to replace the file's own (`[]` for none; they show in the tvOS transport bar, iOS has no chapter UI), external `subtitles` and `trickplay` thumbnails. Everything but the URL is optional, and all of it is fixed for one load.
- **`EnhancedPlayer`** plays it. `EnhancedPlayer(configuration:)` takes the engine tuning. `load(_:startTime:)` takes an `EnhancedMedia` or a bare URL; from synchronous code it returns at once, and in async code it returns once the file is open, with the duration, chapters and track lists known and playback not yet started. Then `play()`, `pause()`, `seek(to:)` and `stop()`. Observable: `status`, `error`, `currentMedia`, `currentTime`, `duration`, `chapters`, `audioTracks` and `subtitleTracks` (`MediaTrack` values: `index`, `name`, `language`, `isForced`, `isExternal`), and the settable `selectedAudioTrack` and `selectedSubtitleTrack` (nil turns subtitles off; a forced track for the audio's language still shows). `avPlayer` is there for observing.
- **`EnhancedPlayerView(player)`** shows a player with the system controls.

Playback starts on the file's default tracks. Tracks selected after an awaited load returns, before `play()`, are what playback starts with; selected later, they switch at once. A seek before the file is open sets where playback starts.

Showing the view opens the loaded media: probe, server, display matching, then playback once `play()` has been called. Removing the view ends the session wherever it was shown (a full-screen cover, a sheet, a navigation push): the display mode resets, the server stops and the cache is deleted. The player keeps the media, its position and its tracks, so showing it again resumes. Loading other media ends the current session and, while the view is showing, opens the new one. Keep the player in `@State`: a player created anew each time the parent's body runs would start a new session each time. In UIKit, host the view in a `UIHostingController`.

Times are `Duration`s in the file's own timeline, which is also the clock a sidecar subtitle file or a server's chapter list uses. A track's `index` counts from 0 in file order. Subtitle tracks list external subtitles first, in the order they were passed, then the file's own tracks, the same order as the subtitle menu.

**External subtitles** are SRT, WebVTT or ASS / SSA files, by extension or by their first line. They are fetched with the media's headers while the file is probed, up to 10 MB each, decoded as UTF-8 or UTF-16 by their byte order mark, else UTF-8, else Windows-1252. One that can't be fetched or read is logged and left out; playback goes ahead. SRT and WebVTT become a rendition with one WebVTT segment as long as the movie, since the whole file is already in memory; their cues get the same cleanup as embedded text tracks. An ASS script is split into its header and its `Dialogue` lines, which are rewritten into the Matroska block form, and goes through the libass renderer like an embedded ASS track; `fonts:` adds fonts the script needs.

**Trickplay** thumbnails come from sprite sheets described by a `Trickplay` value: the thumbnail size (`width`, `height`), the grid of a sheet (`tileWidth` across, `tileHeight` down), `interval` (milliseconds each thumbnail stands for), `bandwidth` (the sheets' average bit rate) and every sheet URL in order. How many thumbnails there are follows from those: one per `interval` to the end of the video, as far as the sheets hold. AVPlayer only takes scrubbing thumbnails from an I-frame rendition, so the master lists one (`CODECS="mjpg"`, `iframe.m3u8`) with one entry per second of the movie: `iframe_{n}.mp4` is a Motion JPEG fMP4 fragment holding the thumbnail that shows at that second, cut out of its sheet and stamped on the video's clock, so a thumbnail standing for 10 s is served for 10 consecutive seconds. For an HDR file, `iframe.m3u8` waits up to 3 s for a video init or segment to be asked for and is answered 404 if none is: the entry is `VIDEO-RANGE=SDR`, so on an SDR display it is all that is left of the HDR master, and AVPlayer would play the stills as the video instead of refusing the master. The item then fails on the missing playlist, which the player takes as the refusal and moves to `master_sdr.m3u8`. A sheet is fetched with the media's headers when one of its thumbnails is first asked for, decoded once, and every thumbnail in it encoded as its own JPEG and kept for the session. A description that doesn't add up (no size, layout or interval, or no sheets) is logged and left out. A last sheet holding fewer thumbnails than its grid ends at its last whole one.

`EnhancedPlayerConfiguration` sets the segment duration (`hls_time`, default 6), the look-ahead (default 3 segments), HTTP headers for every source (the media's own go over them), the cache directory, the source cache budget and the `logger`. The remuxer isn't usable on its own, because PGS and ASS drawing, forced-subtitle selection, display-mode matching and the SDR fallback all depend on the player.

**Logging** goes through [swift-log](https://github.com/apple/swift-log). By default it goes to the unified system log, subsystem `EnhancedNativePlayer`, which Console.app shows for a device without Xcode attached; pass `logger` to send it through your own handlers instead (`Logger(label: "EnhancedNativePlayer")` for the ones your app bootstrapped). The engine only produces the lines: storing, exporting or uploading them is up to the app. Every line has `category` metadata (`player`, `avplayer`, `display`, `source`, `server`, `remux`, `video`, `subtitles`, `trickplay`, `ffmpeg`), which the default logger turns into the unified log's category, and every line of a playback has a `session` ID, new for each one. A session opens with the device, the configuration, and every stream with what the engine does with it, at `notice`, the lowest level the unified log keeps on disk, with the decisions made along the way (display switch, SDR fallback, restarts). Events (the public calls, AVPlayer's state, stalls, track changes, the app going to the background, thermal state, audio route) are `info`; trouble is `warning` or worse. Nothing is logged per frame or per packet: drawn video is summed up every 30 s, every 5 s while frames come late or are dropped, and once more when it stops. The summary splits a frame's cost into reading packets, decoding, converting and enqueueing against the frame's time budget, says how many frames per second that would allow, how the video thread's time divides between working, waiting with enough queued and waiting on a renderer that takes no more, and tells drops on the way back to the clock after a seek from drops because the decoder fell behind; a message that repeats goes out once per 10 s with a count of the ones held back; each request to the local server is `debug`. FFmpeg's own warnings and errors go to `ffmpeg` instead of stderr. When an item ends, a summary of AVPlayer's access log follows: time watched, startup time, stalls, dropped frames and bytes read.

Requirements: tvOS 17 / iOS 17 / macOS 14, and a source server that answers range requests.

## How it works

1. **Keyframes without scanning.** The file is read in 1 MB blocks (`RemoteFile`) over one connection per reader: each is one range request from where its reader is to the end of the file, read only as far ahead as needed and paused by not reading. Once playback reads on, a prefetcher's connection reads ahead of it and the reader's own closes, so a steady playback holds one connection; a jump to an index or a subtitle read uses its reader's own instead of moving playback's. Those readers jump more than they read on, so theirs ask for bounded ranges instead, one block after a jump and more as the reader reads on, and keep the socket open between them: the next range, wherever it is, needs no new TCP or TLS handshake. A connection a reader is waiting on that brings less than 2 MB in 20 s is replaced by a new one at the same place. A server that answers 429 or 503 gets no new request before its `Retry-After` (up to 60 s), and from then on one connection fewer than it had open; a reader waiting on a block takes the place of one nobody waits on. After a redirect, connections go straight to where it led. libavformat loads the container's own keyframe index, Matroska Cues or the MP4 `stss`, into the stream's index entries. That costs the header, the index and the first cluster: a few requests, typically ~150 ms, instead of a full-file ffprobe pass.
2. **The segment plan.** `SegmentPlan` applies hlsenc's cut rule verbatim. A segment ends at the first keyframe with `pts − start_pts ≥ hls_time × n`, where n counts segments, using an exact `av_compare_ts` comparison. The playlists' EXTINF values match `ffmpeg -f hls -hls_time 6` exactly; the tests check this against real ffmpeg output.
3. **Playlists** are rendered per request: `master.m3u8`, `video.m3u8`, `audio_{n}.m3u8` (which shares every EXTINF with the video), and `subtitle_{n}.m3u8`. Each segment URI carries `?runtimeTicks=` (100 ns) for its start. With a start time, the video and audio playlists carry `EXT-X-START` at it, so AVPlayer's first request is for the segment playback starts in rather than segment 0.
4. **Remux.** Video is a stream copy into fMP4: `hvc1` for HEVC; `dvh1` with dvcC/dvvC (`-strict unofficial`) for Dolby Vision profile 5; `hvc1` with dvcC/dvvC for profile 8; `hvc1` and plain HDR for profile 7. Audio is copied for AAC, AC-3, E-AC-3 (Atmos/JOC kept, `CHANNELS="16/JOC"`) and FLAC. Anything else (DTS, TrueHD, Opus, …) is decoded and re-encoded to FLAC (16- or 24-bit, up to 7.1).
5. **Audio follows the video cuts.** Audio segment k starts with the first audio frame at or after video segment k's first keyframe, for copied packets and FLAC blocks alike.
6. **Window.** Video and audio each have their own pipeline. A run pauses once it is 3 segments ahead of the newest request and resumes as requests advance. A served segment is deleted from disk. A request beyond the window (a seek), for a segment already sent, or for another audio track stops the run, deletes its segments and starts a new run at that segment.
7. **Display mode (tvOS).** The player turns off `appliesPreferredDisplayCriteriaAutomatically` and sets the `preferredDisplayCriteria` of the master playlist's asset itself. It then waits for `isDisplayModeSwitchInProgress` to go true and false again, plus 0.5 s, or for 10 s if no switch starts. The wait is skipped when "Match Content" is off in Settings. Only then does the player get a URL, but the video and the starting audio are produced from the start segment on as soon as the file is probed, so the switch's seconds are spent downloading what AVPlayer asks for first.
8. **Subtitles.** Every subtitle track is a rendition with its own playlist of 10 s WebVTT segments, `subtitle_{t}_{n}.vtt`, on a fixed grid independent of the video cuts. A segment's time follows from its index, so these URIs need no `runtimeTicks`. A request seeks on the keyframe index and reads only that stretch of the file, so a seek gets its cues right away. When a video request moves the run elsewhere (a seek), reads still running for segments more than one before or a minute after the new position stop, so they don't take bandwidth from it. A cue goes in the segment its start lands in and keeps its full duration, even past the segment's end. SRT, plain text, `mov_text` and Matroska WebVTT are read directly from packets, without a decoder. ASS and bitmap tracks (PGS, VobSub, DVB) are listed, but their segments are empty; PGS and ASS are drawn by the player instead (below).
9. **PGS.** HLS can't carry bitmaps, so the player watches the subtitle selection and, when the chosen rendition is a PGS track, draws it itself in `contentOverlayView`, above the video and below the controls. Display sets are read on the same 10 s grid and parsed without a decoder. mkvmerge zlib-compresses PGS by default and this FFmpeg build has no zlib, so such blocks are inflated with Apple's Compression framework; the demuxer's "Unsupported encoding type" message for those tracks is expected. Since a display set can reuse objects and palettes from earlier in its epoch, and a subtitle can start before the segment does, a read also looks back up to 3 segments; only the segments around the playhead stay in memory. The PGS canvas maps to the screen, not to the video, so a subtitle authored on a 16:9 canvas keeps its place over a letterboxed picture. A canvas of another shape is fitted and centered.
10. **ASS / SSA.** These go through [libass](https://github.com/libass/libass) (0.17.5 with its NEON and SSE assembly, which makes heavy typesetting about 9× faster than a plain C build; `scripts/build-libass.sh` builds it with FreeType, FriBidi and HarfBuzz into the dynamic `Frameworks/EPLibass.xcframework`, released with the package like FFmpeg) in the same way: when the chosen rendition is an ASS track, the player draws it in `contentOverlayView`. Events are read on the 10 s grid straight from the Matroska blocks, which are already in the form `ass_process_chunk` takes, with the codec private data as the script header; zlib-compressed tracks are inflated as for PGS. Fonts attached to the file are handed to libass, and anything else is found through CoreText. A read covers the segment under the playhead, the next one, and up to 3 before it, for long signs that started earlier; events stay in the libass track for the session, and ReadOrder drops repeats. Timing is per frame, and the subtitles are presented the way the video is: as timed sample buffers in an `AVSampleBufferDisplayLayer` whose control timebase is the player item's own. Each rendered frame becomes a BGRA buffer the size of the overlay in pixels, with the video frame's presentation time and duration, and the layer's video queue picks the buffer for each refresh the same way, against the same clock, as the video's. Nothing reads a clock on the main thread or in Core Animation, and pauses, seeks, rate changes and stalls follow the timebase by themselves. The frame times are the video packets' own, which the Matroska read walks over anyway, so variable frame rates are exact too; MP4 falls back to the frame rate. Half a second is rendered ahead, since every animated frame is a screen-sized buffer. Rendering uses one libass instance, which keeps up with the typesetting tested so far. The engine can run several (each with its own library, renderer and track holding the same fonts, events and layout, since libass shares nothing safely across threads), splitting a stretch into one run of consecutive frames per instance and joining a still image that carries on from one run into the next back into one sample; raising `ASSRenderEngine.defaultWorkerCount` turns that on. All of a frame's libass images are blended into one bitmap the size of their union by Core Graphics (each libass bitmap is a coverage mask filled with its colour, so heavy typesetting stays fast in a debug build too), at the screen's pixel scale, and runs of identical frames share one sample; stretches with no text share one transparent buffer. A seek anywhere but forward inside the enqueued stretch flushes the layer, image included, before samples for the new place are enqueued, and new events or a new layout replace the enqueued samples from the frame on screen. The script's coordinates map to the video's place on screen, not the whole screen, and colours are mangled by the `YCbCr Matrix` header against the video's matrix the way VSFilter did (a missing header means TV.601; `None` and HDR video leave them alone).
11. **SDR displays.** tvOS cannot report the display's mode, so an HDR file is always offered its HDR master first. If AVPlayer refuses it for the display (`-11868`, `-11848` or `-1002`, within about 60 ms and before any segment is fetched), the player gets `master_sdr.m3u8` instead. Its video is the same stream without a transcode: `SDRBitstreamRewriter` sets the SPS colour description and the `colr` box to Rec. 709 and removes SEI, Dolby Vision RPU / enhancement layer NAL units and the mastering metadata. Audio renditions are shared. For video the engine draws, the SDR master swaps the HEVC HDR placeholder for the H.264 SDR one, and the drawn frames are unchanged.
12. **Video AVPlayer can't decode.** H.264 and HEVC are copied as above, except 10-bit H.264 (High 10). Anything else libavcodec decodes to 4:2:0 at 8 or 10 bits (AV1 through dav1d, VC-1 / WMV3, MPEG-4 Part 2 such as DivX and Xvid, MPEG-2, VP9) is decoded by the engine and drawn by the player, and the system controls work on it as on any other file. AVPlayer still plays a video rendition, since the controls, scrubbing, the display mode switch and the screensaver all follow it: `video_{n}.mp4` carries one 64×64 black frame (18–26 bytes), repeated at the source's frame rate and cut on the same plan, so the audio and every EXTINF are what a copied video would give. The frames are baked in: H.264 tagged Rec. 709 for SDR, HEVC Main 10 tagged BT.2020 with PQ or HLG for HDR, so the master's `VIDEO-RANGE` and the stream agree and the display switches to HDR. The real frames are read from the same block cache as the audio, decoded with every core, converted to NV12 or P010 (in C with NEON, so a debug build keeps up) with the frame's colour description and pixel aspect attached, and enqueued in an `AVSampleBufferDisplayLayer` placed where AVPlayer draws its own picture: inside the `AVPlayerLayer`, above the placeholder and below the layer AVPlayer draws text subtitles in, so SRT and WebVTT keep the system's subtitle style; PGS, ASS and the controls are above it too. That subtitle layer has no public name and is found by its class; if it is ever missing, the picture goes to the bottom of `contentOverlayView`, which hides AVPlayer's text subtitles, and the log says so. The layer's control timebase is the player item's, so the frames follow the clock the audio plays on through pauses, rate changes and stalls, the way the ASS samples do. Half a second is queued ahead, at most 160 MB of frames. A seek anywhere but forward inside the queue flushes the layer, keeping the image on screen, and decodes from the keyframe before the new time; the frame on screen at the target is the first one shown. Three things keep that decode from showing:

- **The server holds the seek's segment.** AVPlayer asks for the segment holding a seek's target right after the seek, reports the target as its current time about 50 ms later, and moves its clock only once that segment is in. So when AVPlayer asks for the video segment its current time is in, the server holds it (`VideoStartGate`) until the frame at that time is queued, at most 5 s, or 2 s after the decoder stops making progress. AVPlayer waits as it does for any slow segment, and picture and sound start together. A load and a resume are held the same way.
- **A seek inside what AVPlayer has loaded asks for nothing**, and AVPlayer loads the placeholder far ahead, since it is tiny. There the decoder catches up after the seek: the image on screen stays until it is back on the clock, rather than stuttering, and while playing, frames nothing refers to aren't decoded meanwhile (except by dav1d, which takes that setting only when it opens).
- **AV1 seeks in the system controls land on a keyframe.** AV1 keyframes are often 5 to 10 s apart, so an exact seek can mean seconds of 4K frames to decode first. A scrub or skip (`playerViewController(_:timeToSeekAfterUserNavigatedFrom:to:)`, tvOS) lands on the keyframe nearest its target instead, if one lies within 10 s and within half the seek's own distance, so a short skip stays a skip; a jump to a chapter's start stays exact, and so does `seek(to:)`.

Once on the clock, frames that would end before it are dropped undrawn, but one is still shown every quarter second, so a decoder that can't keep up gives a slower picture, not a frozen one, and says so in the log.
13. **Stop.** `stop()`, or the view going away, resets the display criteria, shuts the server down and deletes every segment and cached block. When the display switched mode for the stream, the view's disappearance (a dismissal or pop) resets the criteria as it begins and covers the window in black until the switch back has ended (the start notification comes before the TV blanks), or for 3 s if none starts, so the view underneath is never shown in the stream's mode. Without a switch nothing is covered.
14. **Starting tracks.** A track chosen before playback is marked `DEFAULT=YES` in the master in place of the file's default, so AVPlayer's first request is already for it, and is selected in the item's media selection groups before `play()`, in case the system language preference picked another. Choosing a subtitle track, or none, also sets the system caption display type (see the subtitles menu below). The SDR fallback starts with the same tracks and position.
15. **Metadata and chapters.** The media's metadata becomes the item's `externalMetadata`, and chapters its `navigationMarkerGroups` (tvOS), each a timed group with a title and optional artwork. Both are applied to every item, including the SDR fallback's, and only rewritten when they change. Artwork URLs are downloaded once with the media's headers; chapter titles go up at once and their images together once all have loaded.

### Why restarts produce identical segments

A run that starts at segment k must emit exactly what a run from the beginning would, or segment durations and timestamps drift after every seek. The tests check this byte for byte.

- **Cuts come from the plan, not the run.** Every run cuts at the precomputed keyframe timestamps, so the pattern never depends on where the run started.
- **Exact seek.** A restart seeks to the segment's keyframe timestamp from the index with `AVSEEK_FLAG_BACKWARD`, and drops anything before it. The demuxer can only land on that entry or an earlier one, so the "+0.5 s" nudge isn't needed. A nudge could also land on the next keyframe when keyframes are under 0.5 s apart.
- **One absolute clock.** Packets keep their source timestamps plus one fixed offset (the first keyframe lands at 10 s, like Apple's segmenter). movenc runs with `frag_discont` and `use_editlist=0`, so `tfdt` is the true decode time in every run, and `mfhd` is pinned to the segment number.
- **Segments end where the next begins.** Each packet's duration is the distance to the next packet's DTS, so the last sample of a segment ends exactly at the first sample of the next.
- **Matroska DTS.** Matroska stores PTS only. Decode timestamps are assigned per segment: the segment's sorted PTS minus the reorder depth, the same in every run.
- **FLAC.** Transcoded audio uses one encoder per run on a fixed block grid anchored at the track start. Frame numbers are rewritten to their absolute grid position (with CRCs recomputed). The stream is therefore what a single encode of the whole track would produce, which is also the only shape Apple's FLAC decoder accepts.

## Notes and limits

- **Audio labels.** An audio rendition's `NAME` is the `{Language} - {Title} - {Codec}` label, and it carries no `LANGUAGE`, `AUTOSELECT` or `DEFAULT`. AVFoundation's `displayName`, which the AVPlayerViewController audio menu shows, is the `NAME` only for such a rendition: with `AUTOSELECT=YES` or `DEFAULT=YES` it is built from `LANGUAGE` alone (`Unknown` without one), and with a `LANGUAGE` in another language than the system's it is that language's name. With no rendition to autoselect, AVPlayer starts on no audio, so the player selects the starting track itself as soon as the master playlist is read: the `selectedAudioTrack` set before playback, else the container's default, else the first. With no audio `LANGUAGE`, AVPlayer can't tell what language the audio is in, so it offers its generated subtitles (iOS and tvOS 27) whatever the language.
- **Enhance Dialogue** needs the audio session in `.playback` / `.moviePlayback`. The player sets that itself and deactivates the session when it stops.
- **Dolby Vision profile 8** is one variant, as in Apple's HLS authoring spec: `CODECS` is the `hvc1` base layer and `SUPPLEMENTAL-CODECS` is `dvh1.08.LL/db1p` (HDR10), `db4h` (HLG) or `db2g` (SDR). A client without Dolby Vision plays the base layer.
- **HDR10+** is found from the HDR10+ SEI (ITU-T T.35, application 4) in the first video sample, and announced with `SUPPLEMENTAL-CODECS` set to the `CODECS` string plus `/cdm4`, with `VIDEO-RANGE=PQ`. HDR10+ carried only as Matroska BlockAdditional side data is not announced, since it never reaches AVPlayer.
- **Parameter sets only in-band.** Some HEVC files have an empty `hvcC` and carry VPS / SPS / PPS at each keyframe. AVPlayer fails on such a sample entry with CoreMedia `-19601`, so the probe fills the record from the first video packet.
- **Lossy sources in FLAC.** For DTS core, Opus, MP3 and other lossy sources transcoded to FLAC, a restarted run has identical timing. The PCM can differ in the lowest bits, because lossy decoder state never re-converges bit-exactly after a seek. Lossless sources (DTS-HD MA, TrueHD, PCM) are bit-identical.
- **Codecs.** Video is H.264 or HEVC for AVPlayer, or decoded by the engine to 4:2:0 at 8 or 10 bits (see 12); 12-bit and 4:2:2 / 4:4:4 outside H.264 and HEVC are rejected. TrueHD Atmos and DTS:X objects are lost in the FLAC path; only the bed is kept.
- **Keyframe index required.** A file without a keyframe index (Matroska without Cues) is rejected rather than downloaded in full.
- **The subtitles menu on tvOS is AVKit's own, and follows the API.** Its switch follows the system caption display type, which it sets itself: always on when the user turns subtitles on, forced only when they turn them off. So a subtitle selection through `selectedSubtitleTrack`, the starting one included, sets the display type the same way (`MACaptionAppearanceSetDisplayType`) before selecting the rendition. Like the menu's switch, that changes the user's setting for every app. A forced track the player turns on leaves it alone. AVPlayer's automatic selection criteria must stay on for this: with them off, the switch stays off once the user turns subtitles off in the menu, whatever is selected after, until the user turns it on there again.
- **PGS limits.** A PGS track is drawn in SDR even over HDR video, and a subtitle that started more than 30 s before a seek target isn't recovered.
- **ASS limits.** ASS is drawn in SDR over HDR video. An event that started more than 30 s before a seek target isn't recovered until playback reaches its segment again. Fonts named by a script that are neither attached nor on the system fall back to Helvetica Neue.
- **Subtitle labels and selection.** `NAME` is just the language: `English`, then `English (2)`, `English (3)` for later tracks of the same language. Forced tracks are `English (Forced)`, counted separately. The first non-forced track of each language carries the real tag in `LANGUAGE` (`en`), so the menu shows the language name and the system language preference can match it. Forced tracks, later tracks of the same language, and tracks with no known language carry their `NAME` in `LANGUAGE` so the menu keeps them apart. No rendition is marked `FORCED`: AVPlayer turns a forced track on only when the audio's `LANGUAGE` matches, and the audio renditions carry none. Instead the player selects the forced track of the audio's language once the item is ready to play and whenever the audio changes after that, as long as subtitles are off or on a forced track; a track the user picked is left alone. When the new audio has no forced track, the player deselects the forced one. AVPlayer's automatic selection criteria stay on (see the subtitles menu above), but an explicit selection holds under them: AVPlayer doesn't reselect the subtitles on an audio switch, and a forced track the player turns on is drawn with the display type on forced only. `DEFAULT=YES` goes to the `selectedSubtitleTrack` set before playback, else to the first non-forced embedded track with the container's default flag, unless every non-forced embedded track has the flag (Matroska sets it unless a muxer clears it). `AUTOSELECT=YES` goes to that `DEFAULT=YES` rendition only; the other subtitle tracks omit it. `DEFAULT` and `AUTOSELECT` only choose the track; the explicit selection is what turns it on. It waits for the item to be ready because changing the selection while the item loads can leave AVPlayer without its track list, so the Dolby Vision profile and the info panel's video details stay empty until a seek. External tracks are named and labeled by the same rules, counted ahead of the file's own.
- **Subtitle reads in Matroska** cover the segment's stretch of the file, about 12 s plus a GOP, because the cues are interleaved with the video. Those blocks are the ones the video remux needs too, and each segment's cues are kept for the session, so a track is read once per segment. MP4 jumps straight to the cue samples.
- **Drawn video.** HDR is drawn as HDR10 or HLG, without Dolby Vision or HDR10+ metadata. On an SDR display the SDR fallback carries the H.264 SDR placeholder; the drawn frames keep their PQ / HLG tags and the system maps them to SDR. Picture in Picture and AirPlay show AVPlayer's black placeholder. Software decoding sets the ceiling: 4K AV1 needs a recent Apple TV, while VC-1, MPEG-4 Part 2 and 1080p AV1 decode with room to spare. A seek inside what AVPlayer has loaded can't be held, so on a long GOP the image stays a moment while the sound plays on, until the decoder is back on the clock; AV1 seeks from the controls land on a keyframe to keep that short. ASF (WMV) files are not read yet.
- **`master_sdr.m3u8` is a relabel; the player tone maps it.** The bitstream is relabeled Rec. 709 so AVPlayer takes it on an SDR display, but the pixels are still PQ / HLG. The player takes AVPlayer's decoded frames through an `AVPlayerItemVideoOutput`, tags them with the file's real colour (BT.2020 PQ or HLG, plus the container's mastering display and content light level when present), and shows them in an `AVSampleBufferDisplayLayer` over AVPlayer's picture, where the system maps them to SDR. Static metadata carried only in SEI is not read, so such a file is tone mapped with the system's defaults. Picture in Picture and AirPlay show AVPlayer's untouched, washed-out picture. Dolby Vision profile 5 still has wrong colours, since its base layer only makes sense with the RPU.
- **The 10 s wait** also applies when the display already matches the stream, because no switch ever starts.

## Logs

The library logs to the unified system log under the subsystem `EnhancedNativePlayer`, so Console.app shows it on a device without Xcode attached. Choose the Apple TV, filter on `subsystem:EnhancedNativePlayer`, and turn on Action → Include Info Messages. Each playlist and segment request is logged when it arrives and when it is answered, along with source download retries, `AVPlayer`'s item status, waiting reason and error log.

## Tests

Unit tests cover the cut rule, exact arithmetic, FLAC frame renumbering, routing, which video AVPlayer gets and which the engine draws, PGS decoding, SRT / WebVTT / ASS file parsing, the starting-track defaults in the master, and ASS timing, compositing and colour mangling. The end-to-end suite is opt-in, and runs on macOS and on the tvOS Simulator:

```sh
ENP_E2E_URL=http://127.0.0.1:8080/movie.mkv \
ENP_E2E_TRUTH=/path/to/ffmpeg-hls/video.m3u8 \
swift test
```

The end-to-end suite checks:

- probe speed and EXTINF parity with ffmpeg
- byte-identical segments between a continuous run and restarted runs, for video and every audio track
- a seek reads only the file around its target, for video and every audio track
- the 3-segment window and delete-after-send
- cleanup on stop
- real AVPlayer playback, seeking and audio-track switching
- PGS frames read right after a seek matching a full pass of the track, and AVPlayer reporting the selected PGS rendition
- ASS events read right after a seek matching a full pass, attached fonts found, libass drawing an event from its first millisecond, and AVPlayer reporting the selected ASS rendition
- ASS samples switching image at exactly the item time the video frame does, at each frame around several events' starts and ends (paused seeks to a frame's first instant and to 0.5 ms before it, checked against `AVPlayerItemVideoOutput`)
- subtitle segments on the 10 s grid, a segment reading only its stretch of the file, and AVPlayer showing a cue on time after a seek
- external SRT and ASS files listed before the file's tracks, an unreachable one left out, the SRT served whole with its cues moved onto the playlist timeline, and the ASS events reaching libass

A second opt-in suite takes files whose video the engine draws, comma-separated in `ENP_RENDER_URLS`, and checks the placeholder master playing and seeking in AVPlayer, placeholder segments that don't depend on where a run started, decoded frames on the playlist clock with each ending where the next begins, a seek landing on the frame on screen at its target, and, with the frames enqueued on a real player item's timebase, the image on screen after a paused seek being exactly that frame.
